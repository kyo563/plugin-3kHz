# 1. アプリ概要

## 1.1 目的

「待機列整理アプリ」は、外部チャット取得アプリケーションから受け取ったコメントデータを処理し、配信者が指定した文言に反応して、参加希望者の待機列を整理するローカル配信支援アプリである。

OBS上には、現在参加中のユーザー、次回参加予定のユーザー、待機中の人数またはグループ数、受付状態などを表示する。

配信者は管理画面から、受付開始・受付終了、次の参加者への進行、手動追加、手動削除、並び替えなどを行える。

## 1.2 基本コンセプト

```text
外部チャット取得アプリケーションから受け取ったコメントデータを検知し、
参加者の順番待ちを整理してOBSに見やすく表示する。
```

## 1.3 想定用途

本アプリは、以下のような参加型配信での利用を想定する。

* 参加型ゲーム配信
* 参加型麻雀配信
* 配信者を含めて4人で遊ぶゲーム配信
* 視聴者3人を1グループとして扱う順番待ち企画
* 先着順を基本にしつつ、参加回数の少ない視聴者を優先したい配信
* 配信中に受付状態を画面表示したい企画
* 手動管理では参加者の見落としが発生しやすい企画

## 1.4 非対象

以下は初期版の対象外とする。

* 抽選による参加者選定
* 複数配信プラットフォーム同時対応
* クラウド同期
* 複数PC間でのリアルタイム共有
* スマートフォン単体での管理
* OBSネイティブプラグインとしての実装
* 視聴者側参加人数の可変設定
* 金銭や賭けを伴う用途

# 2. 全体構成

## 2.1 推奨構成

初期版は、OBSネイティブプラグインではなく、以下の構成とする。

```text
配信サイトのライブチャット
  ↓
外部チャット取得アプリケーション
  ↓
待機列整理アプリ
  ↓
ローカルDB
  ↓
OBS表示用オーバーレイ
  ↓
OBSブラウザソース
```

## 2.2 画面構成

| 画面      | 用途 |
| ------- | --- |
| `/control` | 配信者または配信補助者が操作する画面（手動調整UI） |
| `/overlay` | 配信画面に載せる表示専用オーバーレイ画面（操作UIなし） |
| `/settings` | 設定画面 |

## 2.3 実装方式

初期版では、ローカルWebアプリ方式を採用する。

```text
管理画面: http://localhost:8080/control
OBS表示: http://localhost:8080/overlay
設定画面: http://localhost:8080/settings
```

OBSにはブラウザソースとして `http://localhost:8080/overlay` を読み込ませる。

# 4. 基本機能

## 4.1 コメント受信（外部連携前提）

本アプリは、配信サイトからの直接チャット取得を主機能としない。
チャット取得は外部チャット取得アプリケーションに一任し、本アプリは受信後の処理を担当する。

`ChatProvider` は、直接取得の抽象化ではなく、外部取得元からデータを受け取る入力口として定義する。

```text
ChatProvider
├─ ExternalChatProvider
└─ ManualTestProvider
```

- `ExternalChatProvider`: 外部コメント取得アプリケーションからコメントデータを受信
- `ManualTestProvider`: 開発・デモ・OBS確認用の手動/テスト入力

外部連携方式は特定方式に固定せず、公式に許可された方法に限定する。

候補（一般論）:
- HTTP
- WebSocket
- ローカルAPI
- 公式プラグイン機構
- 公式に許可されたファイル出力
- その他、外部アプリが明示的に許可する方式

禁止事項:
- 外部取得アプリ本体の改造
- 内部DB直接参照
- 内部設定ファイル解析
- 非公開API利用
- 通信内容解析
- リバースエンジニアリング
- 外部アプリ本体の同梱配布
- 外部アプリのロゴ/素材/ソースコード流用
- 公式と誤認させる表記
- 取得データの二次利用目的保存

受信コメントは以下の内部形式に正規化する。

```json
{
  "source": "external",
  "externalMessageId": "optional",
  "receivedAt": "2026-01-01T00:00:00Z",
  "displayName": "視聴者名",
  "userKey": "temporary-or-provider-user-key",
  "message": "参加希望",
  "badges": {
    "owner": false,
    "moderator": false,
    "member": false
  }
}
```

- `userKey` は外部取得元の一意識別子がある場合のみ使用
- 一意識別子がない場合、同一ユーザー判定精度は低下しうる
- `externalMessageId` は重複処理用の一時データ
- `message` は判定後に長期保存しない

## 4.2 参加希望トリガー検知

join判定は、正規化後コメントに **`参加希望`** を含む場合のみとする。

join対象外（ignore）:

```text
参加希望者
参加希望順
```

joinとして扱わない例:

```text
参加
さんか
join
参加します
参加したい
予約
入ります
はいります
```

判定説明:

- `参加希望` を含むコメントのみ join と判定する
- ただし `参加希望者` / `参加希望順` を含む場合は ignore とする
- `参加希望します` や `こんにちは参加希望` は `参加希望` を含むため join になる
- `参加します` / `参加したい` は join にならない

## 4.3 参加辞退トリガー検知

cancel判定は、正規化後コメントに **`参加辞退`** または **`参加を辞退`** を含む場合のみとする。

cancelとして扱わない例:

```text
辞退
キャンセル
取消
取り消し
やめます
cancel
参加キャンセル
参加をやめます
```

判定説明:

- `参加辞退` または `参加を辞退` を含むコメントのみ cancel と判定する
- `辞退` 単体、`キャンセル`、`取消` は cancel にならない
- join と cancel が同時に含まれる場合は cancel を優先する

## 4.4 待機列管理

基本ルールは以下とする。

* 同一人物判定は `user_id` で行う（`user_id` は `source + userKey` 由来の非可逆ID。`userKey` 生値は保存しない）
* `declared_player_name`（申告名）は表示補助用であり、同一人物判定・取消対象判定には使わない
* NOWが3人未満かつ受付中の場合、新規joinはNOWへ直接補充する
* NOWが満員の場合、joinはwaitingへ追加する
* 同一ユーザーが `current` または `waiting` にいる状態で再joinした場合、既存位置を削除して waiting 最後尾へ移動する
* `current` にいる場合も `current` から外して waiting 最後尾へ移動する
* waiting上位3件（NEXT相当）にいる場合も waiting 最後尾へ移動する
* waiting後方にいる場合も waiting 最後尾へ移動する
* 申告名付き再joinでは `declared_player_name` を更新して waiting 最後尾へ移動する
* 申告名なし再joinでは既存 `declared_player_name` を維持したまま waiting 最後尾へ移動する
* 再join時も `participation_count` は維持する
* 受付停止中は新規join・再joinとも受け付けず、順番と申告名を変更しない
* 参加辞退/参加を辞退を受けた場合、同一 `user_id` を `current` / `waiting` から探して削除する
* 見つからない場合は状態変更せずログのみ記録する
* 管理画面（`/control`）から手動で追加・削除・並び替えできる


### 4.4.1 申告プレイヤーネーム（`declared_player_name`）

構文:

```text
参加希望 名前 たなかたろう
```

仕様:

- `名前` の後ろの文字列を本人申告のゲーム内プレイヤーネームとして扱う
- 管理画面では `YouTube名（申告名）` として表示する
- OBS表示では設定ONの場合のみ `YouTube名（申告名）` として表示する
- 申告名は同一人物判定には使わない
- 参加辞退対象の判定にも使わない
- 同一人物判定は `user_id` で行う
- `user_id` は `source + userKey` 由来の非可逆IDであり、`userKey` 生値は保存しない

## 4.5 OBS表示

OBSブラウザソースに表示する画面を提供する。

表示する基本項目は以下とする。

* タイトル
* 受付状態
* NOW
* NEXT
* 待機人数
* 待機グループ数
* 必要に応じた補足メッセージ

なお、ユーザーごとの参加回数は配信画面上には表示しない。

参加回数は、あくまで配信者側の管理画面で確認するための内部情報として扱う。

## 4.6 管理画面操作

管理画面では、以下の操作を行える。

| 操作           | 必須度 | 内容                                        |
| ------------ | --: | ----------------------------------------- |
| 受付開始         |   高 | 参加希望ワードの受付を開始する                           |
| 受付終了         |   高 | 新規参加希望の受付を停止する                            |
| 次へ進める        |   高 | 次回参加予定を現在参加中へ移動する                         |
| 手動追加         |   高 | ユーザー名を指定して待機列に追加する                        |
| 手動削除         |   高 | 指定ユーザーを待機列または現在参加中から削除する                  |
| 並び替え         |   中 | 待機列内の順番を変更する                              |
| 参加回数修正       |   中 | ユーザーごとの参加回数を修正する                          |
| 申告名編集/削除      |   中 | `declared_player_name` を編集または削除する                 |
| 全リセット        |   高 | 現在参加中・待機列を初期化する                           |

補足:
- `/overlay` は表示専用で、操作UIを出さない
- `/control` は配信者操作用
- OBS上で操作する場合は `/control` をOBSカスタムブラウザドックとして追加する
- waitingはドラッグ＆ドロップで並び替え可能
- 右クリック操作: 待機列最後尾へ移動 / 削除 / 申告名編集 / 申告名削除
- 操作対象判定は `user_id` のみを使う
- `declared_player_name` は操作対象判定に使わない
- プレースホルダー「参加者募集中」は操作対象外

# 5. 待機列仕様

## 5.1 基本モード

初期版では、視聴者3人を1グループとして扱う固定モードのみを対象とする。

```text
配信者 1人 + 視聴者 3人 = 合計4人
```

そのため、1人参加モードや任意人数グループ機能は初期版では実装しない。

## 5.2 グループ人数

グループ人数は、視聴者3人で固定する。

設定画面での人数変更機能は不要とする。

```text
NOW枠: 最大3人
NEXT枠: 最大3人
1グループ: 視聴者3人
```

## 5.3 表示分類

OBS表示上では、待機列を以下に分類して表示する。

```text
NOW
NEXT
QUEUE
```

### OBS表示ラベルについて

従来の「現在参加中」に相当する枠を、OBS表示上では NOW と表記する。

OBS表示では、配信画面上の視認性を優先し、以下の短いラベルを使用する。

- NOW
- NEXT
- QUEUE

`NOW` は、実際に対局中であることだけを意味するものではなく、
直近で扱う参加枠、または現在進行中の参加枠を表す。

そのため、NOW枠が3人未満で受付中の場合、
新規参加希望者はNEXTやQUEUEではなく、NOW枠の空き枠へ直接補充する。

この仕様は、直近対局の不足枠を埋めるための基本動作である。

表示例は以下とする。

```text
NOW
Aさん / Bさん / Cさん

NEXT
Dさん / Eさん / Fさん

QUEUE
あと2グループ

受付中
```

## 5.3.1 DB上の扱い

「次回参加予定」は独立したstatusではない。`waiting` の `sort_order` 上位3件を表示上「次回参加予定」として扱う。

| 区分 | 表記 |
|---|---|
| OBS表示 | NOW / NEXT / QUEUE |
| 管理画面 | 現在枠 / 次回枠 / 待機列（日本語可） |
| DB内部status | `current` / `waiting` / `done` / `cancelled` |

- `current` = NOW
- `waiting` 上位3件 = NEXT
- `waiting` 4件目以降 = QUEUE
- `done` = 参加済み
- `cancelled` = 取消済み

## 5.4 参加希望時の処理

ユーザーが参加希望ワードを送信した場合、以下の順で処理する。

1. メッセージIDの重複確認
2. 投稿者のユーザーIDを取得
3. 検知ワードに一致するか判定
4. 受付状態を確認
5. 現在参加中に空き枠があるか確認
6. 既に待機列または現在参加中にいるか確認
7. 条件に応じて追加、補充、並び直し、または無視する
8. OBS表示を更新する
9. ログに記録する

※ 40秒状態変更ロックは実装済み。

※ NOW枠が3人未満かつ受付中の場合は、新規参加希望者をNEXTやQUEUEではなく、NOW枠の空き枠へ直接補充する。
これは、直近対局の不足枠を埋めるための基本動作である。

## 5.5 同一ユーザーが再度参加希望した場合

同一ユーザーが既に待機列にいる状態で再度参加希望ワードを送信した場合は、以下の仕様とする。

```text
既存の待機予約を削除し、最後尾へ並び直す。
```

例：

```text
変更前:
A / B / C / D / E

Bさんが再度「参加希望」

変更後:
A / C / D / E / B
```

この仕様により、再送信による割り込みは発生しない。

## 5.6 現在参加中ユーザーが再度参加希望した場合

現在参加中ユーザーの再参加希望は、低消化回数優先モードの割り込み判定対象外とする。

現在参加中のユーザーが再度参加希望ワードを送信した場合、以下の仕様とする。

```text
currentから削除し、waiting最後尾へ移動する（現在の参加枠を放棄して並び直す）。
```

- NOWに空きが出ても、再joinユーザーをNOWへ戻さない
- 申告名付き再joinの場合、`declared_player_name` を更新してwaiting最後尾へ移動する
- 申告名なし再joinの場合、既存の `declared_player_name` を維持してwaiting最後尾へ移動する
- `participation_count` は維持する
- 受付停止中は、順番も `declared_player_name` も変更しない

## 5.7 受付終了中の参加希望

受付終了中に参加希望ワードを検知した場合、以下の処理とする。

* 待機列には追加しない
* OBS表示には反映しない
* 管理画面には通知する
* ログには「受付終了中の参加希望」として記録する

## 5.8 取消時の処理

ユーザーが取消ワードを送信した場合、以下の処理とする。

| 状態 | 処理 |
|---|---|
| waitingにいる | waitingから削除する |
| NEXT相当の位置にいる | waitingから削除し、後続が表示上繰り上がる |
| currentにいる | currentから削除する |
| どこにもいない | 状態変更しない。ログのみ残す |

- `参加辞退` / `参加を辞退` を受けた場合、同一 `user_id` を `current` / `waiting` の両方から探して削除する
- 対象が見つからない場合は状態変更せず、ログのみ残す
- 対象判定は `user_id` のみで行う（`declared_player_name` やYouTube表示名では判定しない）
- 40秒状態変更ロックは実装済み

## 5.9 低消化回数優先モード

管理画面に「低消化回数優先モード」のチェックボタンを設ける。

このモードは、参加回数が少ないユーザーを、次回参加予定の範囲内で優先的に参加させるための機能である。

### 5.9.1 モードOFFの場合

通常の先着順で待機列に追加する。

```text
新規参加希望者は、常に待機列の最後尾に追加される。
```

### 5.9.2 モードONの場合

新たに参加希望したユーザーの参加回数が、次回参加予定に入っているユーザーより少ない場合、次回参加予定の範囲へ割り込める。

ただし、割り込みによって次回参加予定から外れるユーザーは、次回参加予定内で最も参加希望が遅かったユーザーとする。

### 5.9.3 判定例

前提：視聴者3人固定の場合。

```text
NOW
Aさん / Bさん / Cさん

NEXT
Dさん 2回目予定
Eさん 2回目予定
Fさん 2回目予定

待機列
Gさん / Hさん
```

ここで、参加回数0回のXさんが参加希望した場合：

```text
NEXT
Dさん / Eさん / Xさん

待機列
Fさん / Gさん / Hさん
```

この場合、Dさん・Eさん・Fさんはいずれも同じ参加回数であるため、次回参加予定の中で参加希望が最も遅かったFさんが繰り下げ対象となる。

### 5.9.4 割り込み条件

割り込み条件は以下とする。

1. 低消化回数優先モードがONである
2. 新規参加希望者が現在参加中ではない
3. 新規参加希望者の参加回数が、次回参加予定内の少なくとも1人より少ない
4. 次回参加予定が既に3人で埋まっている
5. 新規参加希望者が40秒状態変更ロック中ではない

上記を満たす場合、新規参加希望者は次回参加予定に入る。

繰り下げ対象は、次回参加予定内で以下の条件により決定する。

1. 新規参加希望者より参加回数が多いユーザーを候補にする
2. 候補が複数いる場合、参加希望時刻が最も遅いユーザーを繰り下げる
3. 繰り下げられたユーザーは、待機列の先頭に移動する

### 5.9.5 注意点

この機能は、完全な抽選や自動公平化ではなく、参加回数の少ない人を次回枠に入りやすくするための補助機能である。

そのため、管理画面から手動で順番を調整できる余地は残す。

## 5.10 40秒状態変更ロック（実装済み）

同一ユーザーによる短時間の参加・取消スパムを防ぐため、状態変更後40秒間は同一ユーザーの再状態変更をロックする。

- 対象はコメント由来の参加希望・参加辞退・参加希望再送（並び直し）
- ロック中は状態変更しない。参加希望 名前 <申告名> でも申告名を更新しない
- /control 手動操作は対象外
- 判定は user_id 単位。declared_player_name は判定に使わない
- userKey生値は保存しない
- cooldown_seconds の既定値は40秒

**実装状況（2026-05-27時点）:** 実装済み。

対象となる状態変更は以下とする。

* 参加希望から辞退
* 辞退から再度参加希望
* 参加希望の再送による並び直し
* 取消の連投

### 5.10.1 基本仕様

```text
同一ユーザーが参加希望または取消によって状態変更された場合、
その時刻から40秒間、次の状態変更を無効にする。
```

40秒以内に再度対象ワードを送信した場合は、以下の処理とする。

* 待機列は変更しない
* OBS表示には反映しない
* 管理画面ログには「ロック中の操作」として記録する
* 必要に応じて管理画面にのみ通知する

### 5.10.2 例

```text
00:00 Aさん 参加希望 → 受付
00:20 Aさん 取消 → ロック中のため無効
00:41 Aさん 取消 → 有効
```

```text
00:00 Aさん 取消 → 受付
00:15 Aさん 参加希望 → ロック中のため無効
00:41 Aさん 参加希望 → 有効
```

## 5.11 OBS表示名の制限

YouTubeの表示名には、長い文字列、絵文字、環境依存文字が含まれる場合がある。

OBS表示の崩れを防ぐため、OBS表示画面では以下の制御を行う。

* 表示名は最大15文字程度を目安に省略表示する
* CSSで `text-overflow: ellipsis;` を使用する
* 折り返しによるレイアウト崩れを防ぐ
* 管理画面では元の表示名を確認できるようにする
* 必要に応じて表示名を手動上書きできるようにする

# 6. 進行管理仕様

## 6.1 「次へ進める」ボタン

管理画面に「次へ進める」ボタンを配置する。

このボタンを押すと、以下の処理を行う。

1. 現在参加中にいる実在ユーザーのみ participation_count を加算する
2. 次回参加予定のユーザーまたはグループを現在参加中へ移動する
3. 待機列から次のユーザーまたはグループを次回参加予定として表示する
4. OBS表示を更新する
5. 操作ログに記録する

## 6.2 初回開始時

まだ現在参加中が空の場合、「次へ進める」ボタンを押すと、最初の参加者または最初のグループを現在参加中へ移動する。

## 6.3 次回参加予定が不足している場合

次回参加予定人数が3人に満たない場合も表示する。

例：

```text
NEXT
1. Aさん
2. Bさん
3. 参加者募集中
```

不足枠の表示文言は以下で固定する。

```text
参加者募集中
```

## 6.4 参加者3名未満で「次へ進める」を押した場合

参加者が3名未満でも、「次へ進める」ボタンによって現在参加中へ移動できる。

この場合、参加表明済みメンバーの名前と、不足枠として「参加者募集中」を表示する。

「参加者募集中」は表示用プレースホルダーであり、SQLiteの永続データには保存しない。

例：

```text
NEXT
1. Aさん
2. Bさん
3. 参加者募集中
```

この状態で「次へ進める」を押した場合：

```text
NOW
1. Aさん
2. Bさん
3. 参加者募集中
```

この不足枠はクローズせず、受付中であれば後続の参加希望者を現在参加中の空き枠へ補充できるものとする。

## 6.5 参加者が来ない場合

参加者が不在、反応なし、辞退などの場合は、管理画面から手動削除する。

自動スキップ機能は初期版では必須としない。

# 8. チャット判定仕様

## 8.1 判定方式

現行MVPの判定は、正規化後コメントに対する固定ルール判定とする。

1. join候補: `参加希望` を含むコメントのみ
2. join除外: `参加希望者` / `参加希望順` を含む場合は ignore
3. cancel候補: `参加辞退` または `参加を辞退` を含むコメントのみ
4. joinとcancelが同時に成立した場合は cancel を優先

## 8.2 初期推奨

現行MVPでは「初期推奨」ではなく、以下を固定仕様として扱う。

### joinになる例

- `参加希望`
- `参加希望します`
- `こんにちは参加希望`

### joinにならない例

- `参加します`
- `参加したい`
- `参加`
- `さんか`
- `join`
- `予約`
- `参加希望者`
- `参加希望順`

### cancelになる例

- `参加辞退`
- `参加を辞退`

### cancelにならない例

- `辞退`
- `キャンセル`
- `取消`
- `取り消し`
- `やめます`
- `cancel`

## 8.3 誤検知対策

現行MVPでは、以下を誤検知/誤操作対策として採用する。

- join除外語の固定適用（`参加希望者` / `参加希望順`）
- cancel優先（joinとcancel同時成立時）
- 40秒状態変更ロック
- 管理画面（`/control`）からの手動補正
- 操作ログ（`operation_logs`）による確認

将来検討:

- 参加希望ワード/参加辞退ワード編集
- NGワード設定
- モデレーター・配信者コメントの除外設定

# 10. 例外処理

## 10.1 同名ユーザー

同名ユーザーが存在する場合も、`userKey`（または暫定ID）を基準に別ユーザーとして扱う。

OBS表示上で区別できない場合は、管理画面で表示名を手動変更できるようにする。

## 10.2 表示名変更

ユーザーがYouTube上の表示名を変更した場合、最新の表示名に更新する。

ただし、手動上書き表示名が設定されている場合は、OBS表示では手動上書き名を優先する。

## 10.3 アプリ再起動

アプリ再起動時には、SQLiteから以下を復元する。

- 受付状態
- NOW
- waiting
- `priority_mode`
- `cooldown_seconds`
- `show_declared_player_name_on_overlay`
- `user_action_locks`
- `operation_logs`
- `participants` に保存されている `participation_count`

注意:

- 現行MVPでは、待機列から完全に外れたユーザーの恒久履歴テーブルは未実装
- 参加回数の本格的な履歴管理は将来実装候補

## 10.4 外部チャット取得アプリケーション連携切断

外部チャット取得アプリケーション（ExternalChatProvider）との連携が切断された場合、以下の処理を行う。

* 管理画面に接続エラーを表示する
* 自動再接続を試行する
* OBS表示は最後の状態を維持する
* 復旧後、未処理メッセージを可能な範囲で取得する（ベストエフォート）
* 取得方式によっては切断中メッセージを完全復元できないため、管理画面に警告を表示する

## 10.5 OBS表示停止

OBS表示が更新されない場合に備え、管理画面に以下を用意する。

* 表示更新ボタン
* オーバーレイURL再読み込み案内
* 接続状態表示

## 10.6 操作ミス

操作ミスに備え、Phase 2までに「ひとつ戻す」機能を実装する。

初期版では、ログを確認して手動復旧する運用でも可とする。

```text

同一ユーザーが再度参加希望を送った場合、
既存の待機予約を削除し、最後尾へ並び直す。

参加取消ワードを送った場合、
待機列から削除し、後続参加者を繰り上げる。

配信者は管理画面から「次へ進める」を押すことで、
NEXTをNOW枠へ移動できる。

各ユーザーの参加回数はローカルDBに保存し、
配信画面には表示せず、管理画面でのみ確認できるようにする。

低消化回数優先モードがONの場合、
新規参加希望者の参加回数がNEXTの参加者より少なければ、
NEXT枠へ割り込める。

このとき、NEXTから繰り下げられるのは、
割り込み対象候補の中で参加希望時刻が最も遅いユーザーとする。
```

---

# 16. 判断

本アプリは、OBSネイティブプラグインとして作るよりも、ローカルWebアプリとして作り、OBSブラウザソースで表示する構成が現実的である。

理由は以下である。

* OBSネイティブプラグインは開発難度が高い
* ローカルWebアプリならHTML/CSS/JavaScriptで表示を作りやすい
* OBSブラウザソースとの相性が良い
* 管理画面と表示画面を分離できる
* 将来的にElectronやTauriで配布アプリ化しやすい

したがって、初期開発では以下の方針を採用する。

```text
ローカルWebアプリ + SQLite + OBSブラウザソース
```

# 18. 旧Chrome拡張実装からの転用方針

## 18.1 採用する設計資産

### 18.1.1 視聴者3人固定

旧実装では `MAX_PLAYERS = 3` として次回候補を3人単位で扱っている。

現行仕様でも、配信者1人 + 視聴者3人 = 合計4人で遊ぶ参加型ゲームを主対象とするため、この考え方は採用する。

ただし、現行仕様では人数可変機能は実装しない。

### 18.1.2 参加順 joinNo

旧実装では、参加者登録時に `joinNo` を付与している。

現行仕様でも、以下の用途で参加順を保持する。

* 同回数ユーザー同士の優先順位判定
* 低消化回数優先モードにおけるタイブレーク
* 管理画面での参加履歴確認
* ログ調査

ただし、現行仕様では `joinNo` だけでなく、実際の参加希望時刻 `joined_at` も保存する。

### 18.1.3 参加回数 count

旧実装では、各参加者に `count` を持たせ、`+1` ボタンで参加回数を加算している。

現行仕様では、これを `participation_count` としてSQLiteに保存する。

基本処理は以下とする。

* 「次へ進める」操作時に、現在参加中だったユーザーの参加回数を自動加算する
* 管理画面では手動補正できる
* OBS表示には参加回数を出さない
* 管理画面のユーザー名横に `[参加: 2回]` のように表示する

### 18.1.4 低消化回数優先モードの評価軸

旧実装では、参加者を以下の順で並べていた。

1. `count` が少ない順
2. `count` が同じ場合は `joinNo` が若い順

この考え方は、現行仕様の「低消化回数優先モード」に採用する。

ただし、旧実装のように待機者全体を毎回完全ソートして次回候補を再構成するのではなく、現行仕様では次回参加予定への割り込み判定に限定して使う。

現行仕様の基本ルールは以下とする。

* 通常時は先着順
* 低消化回数優先モードON時のみ、参加回数の少ない新規参加者が次回参加予定へ割り込める
* 繰り下げ対象は、新規参加者より参加回数が多いユーザーのうち、次回参加予定内で参加希望が最も遅いユーザー
* 繰り下げられたユーザーは、次グループの先頭へ移動する
* 既存待機者の再送は割り込み判定の対象にせず、通常の並び直し扱いとする

### 18.1.5 重複メッセージ処理

旧実装では `processedMessageKeys` によって、同一メッセージの重複処理を防いでいる。

現行仕様でも重複処理は必須とする。

優先順位は以下とする。

1. YouTube側の `messageId` が取得できる場合は `messageId` を優先する
2. `messageId` が取得できない場合は、以下の複合キーをフォールバックとして使う

* `userKey`（外部取得元が提供する場合）
* `normalizedAuthorName`
* `normalizedMessage`
* `publishedAt` の秒単位丸め値

旧実装のように、重複キーが増え続けないよう上限を設ける。

例:

* `processedMessageKeys` が 2000件を超えた場合、古いものを削除して1000件程度に圧縮する

### 18.1.6 チャット取得経路のヘルスチェック

旧実装では、DOM取得経路と補助API取得経路の状態を `domSourceHealthy` / `apiSourceHealthy` として持っていた。

現行仕様ではChrome拡張を採用しないため、DOM監視を主方式にはしない。

ただし、以下の考え方は採用する。

* チャット取得処理を `ChatProvider` として抽象化する
* 取得経路ごとに接続状態を持つ
* 管理画面に現在の取得状態を表示する
* 取得失敗時はOBS表示を壊さず、最後の状態を維持する
* 将来的に取得方式を差し替えられるようにする

例:

```text
ChatProvider 状態:
- connected
- reconnecting
- disconnected
- error
```

### 18.1.7 表示名の安全処理

旧実装には `escapeHtml()` があり、表示名をHTMLへ出力する際のエスケープ処理がある。

現行仕様でも以下を必須とする。

* OBS表示、管理画面ともにHTMLエスケープを行う
* 長すぎる表示名はOBS表示で省略する
* 元の表示名は管理画面で確認可能にする
* 管理画面から表示名を手動上書きできるようにする

OBS側では以下のCSS方針を採用する。

```css
.name {
  overflow: hidden;
  white-space: nowrap;
  text-overflow: ellipsis;
}
```

### 18.1.8 +1 ボタンの扱い

旧実装では、ユーザーごとに `+1` ボタンを押して参加回数を加算していた。

現行仕様では、「次へ進める」ボタンによって現在参加中ユーザーの参加回数を自動加算するのが基本とする。

ただし、配信中の事故対応や修正用に、管理画面で以下の手動補正機能を用意する。

* `+1`
* `-1`
* 任意回数へ修正

これはOBS画面には出さない。

## 18.2 採用しない旧仕様

### 18.2.1 Chrome拡張としての配布

旧実装はChrome拡張だが、現行仕様では採用しない。

現行方針は以下とする。

```text
ローカルWebアプリ + OBSブラウザソース + 管理画面 + SQLite
```

### 18.2.2 YouTubeページ上へのUI注入

旧実装ではYouTubeページ上に管理小窓を注入している。

現行仕様では採用しない。

理由は以下である。

* OBS表示と管理画面を分離するため
* 配信画面に載せる表示をOBSブラウザソースとして制御するため
* YouTubeページDOM変更の影響を受けにくくするため

### 18.2.3 メモリ保持のみ

旧実装ではデータがメモリ保持のみで、タブ再読み込みにより消える。

現行仕様ではSQLite保存を必須とする。

保存対象は以下とする。

* NOW
* NEXT
* 待機列
* 参加回数
* 表示名上書き
* 操作ログ
* 設定値
* 40秒ロック解除時刻

### 18.2.4 参加希望 固定

旧実装では検知キーワードが `参加希望` 固定である。

現行仕様では設定可能にする。

* 参加希望ワード
* 取消ワード
* 完全一致
* 前方一致
* 部分一致は初期OFF

### 18.2.5 text.includes(KEYWORD) 判定

旧実装の `includes` 判定は誤検知が多いため、現行仕様では採用しない。

現行仕様では以下を採用する。

* 完全一致
* 前方一致
* 前後空白無視
* 全角半角正規化

現行MVPでは固定ルールとして `参加希望` を含むコメントをjoin候補とし、除外語（`参加希望者` / `参加希望順`）のみをignoreする。

### 18.2.6 表示名ベースの同一人物判定

旧実装では表示名を主な識別子としている。

現行仕様では、取得できる場合は `userKey` を優先する。

優先順位は以下とする。

1. `userKey`
2. provider固有ID
3. 表示名ベースのフォールバックID

表示名ベースの識別は、最後の代替手段とする。

### 18.2.7 待機者全体の完全自動ソート

旧実装では、`count` と `joinNo` で全体を並べ替えて次回・次々回候補を算出している。

現行仕様では、通常の待機列は先着順を基本とする。

低消化回数優先モードON時のみ、次回参加予定枠への限定的な割り込みを行う。

この違いを現行仕様として維持する。
